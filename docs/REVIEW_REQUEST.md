## 1. 目的と背景

- 2025年12月31日に終了したオンライン将棋「**将棋倶楽部24**」の後継を目指す。
- 24の良さ（本格派・落ち着いたデザイン・PCで無料・観戦文化・厳しめのレーティング）を受け継ぎ、現代的なWeb技術とAI練習機能を足す。
- 24は「PC無料で人を集め、スマホの利便性に課金（月350〜490円）」＋「社員1人」の超低コスト運営だった。同じく**1人で回せること**を最重要の設計条件にしている。

## 2. 現在の構成

| 項目 | 内容 |
|---|---|
| サーバー | ConoHa VPS（メモリ2GB / CPU 3コア / Ubuntu 24.04）。同じVPSで別アプリ（droneops 等）も稼働 |
| 実行環境 | Node.js 22（systemd で常駐）、nginx リバースプロキシ、Let's Encrypt で HTTPS |
| サーバー側 | Express + Socket.io（WebSocket） |
| 保存 | SQLite（Node 内蔵の `node:sqlite`、`data/dojo.db` 1ファイル） |
| クライアント | 素の HTML / CSS / JavaScript（フレームワークなし）、PC・スマホのブラウザ |
| AI | **利用者のブラウザ内で実行**。Fairy-Stockfish（WASM、将棋モード）。使えない環境では自前の簡易AI（Web Worker）に自動で切り替える |
| 規模 | 約2,200行（テスト・設置スクリプト込み） |

**設計方針**：サーバーは「マッチング・指し手の検証と中継・対局時計・チャット・部屋管理・保存」だけを担当する。AI計算はサーバーで一切しない（2GBのVPSで耐えるため）。

### ファイル構成
```
server/server.js         マッチング・指し手検証・時計・チャット・部屋管理・API
server/db.js             SQLite（players / games テーブル）
public/js/shogi-core.js  ルールエンジン（サーバーとブラウザで同じコードを使用）
public/js/shogi-ai.js    AIマネージャー（Fairy-Stockfish → 内蔵AI に自動フォールバック）
public/js/ai-worker.js   内蔵AI（αβ探索・静止探索・駒得評価）
public/js/shogi-ui.js    盤・持ち駒・成り選択の描画と操作
public/js/client-ws.js   Socket.io クライアント（自動再接続・トークン保持）
public/js/app.js         画面の流れ（ロビー / 人間対局 / AI対局 / 観戦 / 棋譜再生）
deploy/setup.sh          1行で設置・更新できるスクリプト
test/                    ルール・保存・サーバーの自動テスト
```

## 3. 実装済みの機能

**対局**
- 人間同士のオンライン対局。持ち時間は24と同じ4種類（早指1分+30秒 / 早指2 0分+30秒 / 15分+60秒 / 長考30分+60秒）。
- **反則判定はサーバー側でも実施**：王手放置、二歩、打ち歩詰め、行き所のない駒、千日手（同一局面4回で引き分け）、連続王手の千日手（王手側の負け）、詰み。
- 対局時計はサーバーが管理（持ち時間＋秒読み、通信遅延の猶予1秒、時間切れ負け）。
- 投了、切断後60秒で負け、再接続すれば同じ対局に復帰。
- 成・不成の選択、王手表示、最終手のハイライト、盤の反転。

**AI練習**
- 5段階の強さ、先手・後手・ランダム、ヒント機能。
- **対局待ちの間はAIと練習し、相手が見つかると自動で人間対局に切り替わる**（過疎対策）。

**コミュニティ・記録**
- 観戦（対局中の一覧からタップ）、ロビーチャット、対局室チャット（感想戦用）。
- Elo方式のレーティング（初期1500、K=32）、勝敗記録、レーティング順位（上位20人）。
- 全対局の棋譜を保存し、過去の対局を棋譜再生（◀▶・矢印キー・棋譜クリックで移動）。
- 棋譜コピー（日本語表記＋USI形式）。

**運用**
- `deploy/setup.sh` を1行実行するだけで、Node・nginx・自動起動・HTTPSまで設定。同じコマンドで更新もできる（保存データは消えない）。
- 既存サイトと同じVPSで共存できるよう、ドメインごとに nginx の設定を分けている。

## 4. テストの状況

- ルールエンジン：初期局面からの全合法手数（perft）が3手先まで既知の正解値（30 / 900 / 25,470）と一致。二歩・打ち歩詰め・千日手・連続王手・詰み・棋譜表記などの個別テストも合格。
- 保存：プロセスを再起動してもレーティング・戦績・棋譜が残ることを確認。
- サーバー：2クライアントでの対局（マッチング、手番違い・反則手の拒否、時計、チャット、投了、時間切れ、切断からの復帰、保存API）が合格。
- ブラウザ：2つのブラウザでの対局、待ち時間AI→人間対局への切り替え、棋譜再生を目視で確認。
- **未整備**：CI（自動テストの常時実行）、ブラウザE2Eテストの自動化、負荷試験。

## 5. 自覚している弱点・未実装（特に意見がほしい部分）

### アカウント・本人確認
- 会員登録がなく、**ブラウザに保存したランダムなトークンだけで本人を識別**している。ブラウザのデータを消すとアカウントを失う。別の端末に引き継げない。
- 名前は自由入力で重複可。**なりすましができる**。
- 24は「携帯番号1つにつき1ID」（SMS認証）で複アカを防いでいた。こちらは対策なし。

### 不正対策
- **ソフト指し（AIを見ながらの対局）の検出がない**。AIがブラウザに入っているので、むしろやりやすい。
- 複アカによるレーティング操作、わざと負けてレートを下げる行為への対策もない。

### レーティング・マッチング
- マッチングは持ち時間ごとの先着順だけ。**レーティングの近い相手を選ぶ仕組みがない**。
- 24のような「段級位」表示（例：R1500＝初段）がない。
- 相手を指定しての対局申し込み、駒落ち（ハンデ戦）がない。

### ルール
- **入玉宣言（27点法）・持将棋が未実装**。
- フィッシャールール（1手ごとに時間加算。24では2018年に追加）が未実装。

### 安定性・運用
- 対局中の情報はメモリに持っているため、**サーバーを再起動すると進行中の対局は消える**（保存済みの棋譜・レーティングは残る）。
- 1プロセス構成なので、同時接続数の上限が不明（負荷試験をしていない）。
- 連投制限はチャットのみ。指し手・対局待ちなど他の操作には回数制限がない。
- バックアップ（自動コピー）がまだ設定されていない。
- ドメインが仮（sslip.io）。

### チャット・コミュニティ
- 荒らし対策がHTMLタグ除去と連投制限だけ。NGワード、ブロック、通報、管理者機能がない。

### AIの強さ
- Fairy-Stockfish は将棋用のNNUE評価ファイルを読み込んでいないため、**古典的な評価関数で動いている可能性が高い**（未検証）。最強レベルでもアマ有段者には物足りないかもしれない。
- 内蔵AI（予備）はかなり弱い（数手読みの駒得評価のみ）。

### 使い勝手
- 駒の操作はタップ（クリック）のみで、ドラッグ操作がない。
- 駒音などの効果音がない。
- KIF・CSA形式のファイル保存がない。対局後のAI解析（悪手の指摘など）がない。

### ライセンス・法務
- Fairy-Stockfish は **GPL-3.0**。ブラウザに配信するのは「配布」にあたるので、ライセンス表記とソースの案内が必要（まだサイトに書いていない）。リポジトリ自体にも LICENSE ファイルがない。
- 利用規約・プライバシーポリシーがない。

### 収益化
- まだ何も実装していない。24の「スマホ課金」に相当する仕組みの検討が必要。

## 6. レビューしてほしい観点（質問）

1. **1人運営で続けられるか**：今の構成で、運営の手間が増えそうな部分はどこか。自動化すべきものは何か。
2. **最優先で直すべき点**：上の弱点のうち、公開して人を集める前に必ず直すべきものはどれか。優先順位をつけてほしい。
3. **アカウント設計**：SMS認証・メール認証・Googleログインなど、1人運営でも維持しやすく、複アカ・なりすましを防げる方法はどれか。
4. **ソフト指し対策**：個人で実装できる現実的な検出方法はあるか（AIの推奨手との一致率、考慮時間の分布など）。
5. **人を集める方法**：過疎を避けるために、初期のユーザー獲得で何をすべきか（定時大会、SNS、24の元ユーザーへのアピールなど）。
6. **収益化**：PC無料を維持しつつ、24より現代的な収益モデルは何か（サブスク、広告、指導対局、棋譜解析の有料化など）。
7. **技術的な欠陥**：コード（特に `server/server.js` と `public/js/shogi-core.js`）に、セキュリティ上の問題、競合状態（同時操作で壊れる箇所）、メモリリークなどはあるか。
8. **同時接続の限界**：メモリ2GBのVPS・1プロセスで、何人くらいまで耐えられそうか。先に手を打つべき箇所はどこか。
9. **24との差別化**：24の元ユーザーが「移ってもいい」と思うために、何が必要か。
